Try searching the archive ↗

Podcast episodes are often organized around titles and descriptions. Listeners, however, may remember a feeling, a question, or a particular exchange. That creates a gap between how content is organized and how people recall it.

That got me thinking: What if you could search a podcast by the conversation you remember, instead of the episode it came from? Listeners can spend less time hunting through episodes and more time revisiting meaningful moments. Creators are able to make older conversations discoverable beyond their original release date. And what better way than to explore this using one of my favorite podcasts!

Searching by meaning

Perfect Person Archive is a fan-made semantic search engine. A listener can describe a situation in everyday language and get relevant transcript passages with links to the original moments.

Using transcripts

The system processes timestamped transcripts once, stores passage embeddings, and compares each new search query against them.

  1. 01

    Collect timestamped transcripts

    Start with YouTube episode metadata and available transcripts. Keep each passage's source episode and start time.

  2. 02

    Split the transcript into overlapping passages

    Create approximately 150-word chunks, advancing 120 words at a time. The 30-word overlap helps retain context at boundaries.

  3. 03

    Encode each passage

    Use all-MiniLM-L6-v2 to create normalized, 384-dimensional sentence embeddings. Store the passage metadata in CSV and the vectors in NumPy.

  4. 04

    Rank by semantic similarity

    Embed the query with the same model, compute dot products with the normalized stored vectors (equivalent to cosine similarity), and rank the matches.

  5. 05

    Return the episode and timestamp

    Show a short excerpt, a similarity score, and a YouTube link. Currently, the timestamp points to the start of the retrieved chunk.

Technical tradeoffs

Building a usable search experience required decisions about how to represent conversations, what to return, and how much infrastructure to introduce.

DECISION 1

Fixed-size vs. semantic chunking

I experimented with detecting topic boundaries using changes in similarity between adjacent passages. But jokes and tangents can look like topic changes. I chose overlapping fixed-size chunks as a predictable baseline.

Chose: 150-word chunks, 30-word overlap
DECISION 2

NumPy vs. a vector database

With 8,010 embeddings, a NumPy matrix keeps retrieval straightforward and easy to inspect. A dedicated vector index may make sense if the corpus or traffic grows substantially.

Chose: normalized embeddings + matrix dot products
DECISION 3

Retrieval vs. generated answers

Rather than generating summaries, the first version links people back to what was actually said. A future RAG feature could synthesize multiple passages, but it would need careful citation and grounding checks.

Chose: source-first semantic search
DECISION 4

Relevance vs. variety

Returning only the highest-scoring chunks could crowd the results with multiple excerpts from one episode. I currently show at most one result per episode, trading some recall for broader discovery.

Chose: one top-ranked passage per episode

Future improvements

HIGH PRIORITY

Expand coverage

Only 54 of 225 episodes are currently indexed. Missing transcripts limit what can be found.

HIGH PRIORITY

Evaluate retrieval

Create a human-labeled query set and compare ranking and chunking strategies.

HIGH PRIORITY

Improve timestamp precision

Align links with the most relevant sentence instead of the chunk start.

LATER

Explore hybrid search

Combine lexical matching with embeddings for exact names, memorable phrases, and broader concepts.

LATER

Experiment with grounded RAG

Offer cited cross-episode summaries without replacing the original podcast moments.

Other limitations include transcription errors, context lost at chunk boundaries, and the possibility that semantic similarity produces plausible but irrelevant matches.
